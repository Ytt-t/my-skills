# 验收标准写法参考

> 验收标准是 PRD 里"做到什么算完成"的定义。写不好，开发和测试就会来回问。对应 `SKILL.md` 的 Step 9 与 v0.3「可落地检查」。

## 一、推荐格式：Given / When / Then

```
Given：前提条件（什么状态下开始）
When：触发动作（用户做了什么）
Then：可验证的结果（系统应如何响应）
```

**示例：**
```
Given：用户已经上传有效周报
When：点击"生成团队总结"
Then：
- 系统读取本周有效周报
- 生成团队进度摘要
- 汇总未完成事项
- 标记潜在风险
- 每条结论可追溯到对应周报
```

## 二、把模糊质量词改成可测项

**模糊词（❌ 不要用）** → **可测项（✅ 用这个）**

| ❌ 模糊 | ✅ 可测 |
|--------|--------|
| 完全一致 | 字体属性保持一致（字体名/字号/加粗/斜体/颜色） |
| 版式与原文件一致 | 图片（含照片）位置保持一致 |
| 页面数不变 | 页面数量与原文件一致；若不一致，系统明确提示 |
| 文本正常显示 | 文本溢出检测通过，或有溢出则提示 |
| 高质量总结 | 每条结论可追溯到对应周报 |
| 准确、流畅 | 未出现原内容不存在的事实信息 |
| 快速响应 | 单次改写耗时 < X 秒（基线先标【待采集】） |

规则：**验收里的每个形容词，都要能被"怎么测"回答**。测试人员问"一致的标准是什么？"时，PRD 里必须已有答案。

## 三、异常场景也要写

只写正常流程的 PRD 是不完整的。至少为每个核心功能写一个异常验收：

```
场景（异常 - 扫描件）：
Given：用户上传扫描件 PDF
When：系统尝试识别
Then：系统提示"无法识别文字，请上传可编辑的 Word 或 PDF"，不进入下一步
```

常见异常类型：
- 输入不合法（格式/大小/空值）
- 依赖服务不可用（AI 服务挂了）
- 内容越界（超篇幅、命中事实边界）
- 结果与预期不符（渲染差异、识别偏差）

## 四、AI 功能验收示例

```
场景 A（主流程成功）：
Given：用户上传一份含可识别文本的 .pdf 或 .docx 简历和一段 JD
When：点击"生成改写"并完成
Then：
- 导出的 PDF 满足等级 A 可测项：字体属性一致、图片位置一致、页面数量变化有提示、文本溢出有检测
- 改句未出现原简历不存在的事实信息
- 每段提供"原句 ↔ 改句 ↔ 理由"对照，理由为三段式引用
- 用户可逐段采纳或拒绝，拒绝段保留原句

场景 C（异常 - 事实新增）：
Given：AI 返回某段含原简历无依据的成果描述
When：事实边界校验运行
Then：该段被标记"需人工确认"且不自动落入导出文件
```

## 五、验收自检清单

- [ ] 每个验收都是可测的（没有"高质量""准确""流畅"这类词）
- [ ] 每个核心功能都有 Given / When / Then
- [ ] 核心功能都有至少一个异常场景
- [ ] 涉及 AI 的功能有"AI 失败/越界时怎么办"的验收
- [ ] 有降级等级定义（A 目标 / B 可接受 / C 不接受）
- [ ] 测试人员看完不需要问作者"这个怎么测？"
