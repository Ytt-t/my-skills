# 验收标准规范

> 验收标准是 PRD 里「开发完成后能不能算完成」的唯一依据。写不好，测试只能凭感觉。

## 1. 场景化验收（Given / When / Then）

格式：
```
Given：前置条件
When：用户操作
Then：系统结果（可列举）
```

示例：
```
Given 用户上传有效简历（PDF/Word）
When 点击"生成改写"
Then 系统返回：
  - 逐段改写后文本（段落结构与原简历对应）
  - 每段附带"原句 ↔ 改句 ↔ 理由"
  - 事实边界矩阵中 ❌ 项未被修改
```

## 2. 验收必须可测试（删除形容词）

模糊词 → 可测项对照表：

| ❌ 模糊质量词 | ✅ 可测表述 |
|-------------|-----------|
| 页面流畅 | 点击后 5 秒内展示加载状态，结果渲染不超过 3 秒 |
| 完全一致 | 字体属性保持一致；图片位置偏移 ≤ 2px；页面数量不变 |
| 准确率高 | 可验证事实字段改写新增率 = 0 |
| 体验好 | 完成任务步骤 ≤ 3 步；首次使用无需引导即可完成 |
| 智能 | （删除，AI 不应用「智能」作为验收标准） |

判断：如果测试同学看完验收标准还需要问「一致的标准是什么」，就是没写到位。

## 3. 覆盖三类场景

### 正常流程
用户完成目标任务的主路径。

### 异常流程
- 文件错误（格式不支持 / 损坏 / 超大小）
- 网络失败（超时 / 断连）
- AI 失败（返回异常 / 超时 / 内容缺失）
- 用户取消（中途退出，状态如何保存）

### 边界情况
- 空输入（未上传 / 未填 JD）
- 超长文本（超过模型上下文）
- 特殊格式（扫描件 / 表格型简历 / 多栏）

## 4. 验收标准与功能复杂度匹配

不是所有功能都值得写完整 G/W/T。
- 核心用户价值 → 必须写完整 G/W/T + 异常 + 边界
- 核心 AI 能力 → 必须写，且包含事实边界校验
- 高风险功能 → 必须写异常路径
- 简单辅助功能（如「上传按钮」）→ 一句话规则即可，不必九层展开

## 5. 可追溯验收（AI 产品专项）

AI 改写类功能，验收必须包含可追溯性：
```
Given 用户采纳一段改写
When 查看"改写理由"
Then 理由区展示：
  - 引用的原简历片段
  - 引用的 JD 要求
  - 调整动作
且不存在"为使表述更专业"这类无来源说明
```
