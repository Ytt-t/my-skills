# PRD 产品需求文档写作原则

> 定位：写 PRD 时的「宪法」。SKILL.md 是流程，本文件是判断标准。
> 适用：AI 产品 / 普通功能通用。

## 1. PRD 的核心目标

PRD 不是描述想法，而是**建立共识**。一份合格 PRD 必须明确：

1. 为什么做这个功能（背景与动机）
2. 给谁解决什么问题（用户与场景）
3. 产品应该做到什么（功能与效果）
4. 什么情况下算成功（可验证的成功标准）
5. 哪些事情明确不做（边界，防止需求膨胀）

PRD 的读者是设计师、开发、测试、老板。它的目标是让这四拨人**不需要作者口头解释就能各自开工**。任何一拨人看完还要问作者，这份 PRD 就没写到位。

## 2. 好 PRD 的基本原则

### 原则 1：用户问题优先

不要从功能开始，从问题开始。

错误：
> "增加一个 AI 改写按钮。"

正确：
> "用户每次针对不同岗位修改简历，需要重复复制、调整格式，因此定制成本高。需要降低每次定制的边际成本。"

判断技巧：一句话去掉「AI」后仍然成立，说明描述的是真问题；去掉「AI」就什么都不剩，大概率是「为 AI 而 AI」。

### 原则 2：需求与方案分离

PRD 描述：
- 用户需要什么
- 系统应该达到什么效果

不要提前限制：
- 技术框架
- 数据库选型
- API 实现方式

原则：除非某个技术约束**直接影响产品行为**（例如「必须离线运行」），否则 PRD 只写「系统需要做到什么」，具体实现交给技术方案文档。一旦把实现写死，开发发现更优解时会被 PRD 绑死。

### 原则 3：需求必须可验证

避免：
> "体验更好" / "提高效率" / "更加智能"

改成：
> "用户完成任务步骤从 7 步减少到 3 步"
> "用户可在 5 分钟内完成一次改写"
> "系统对可验证事实字段的改写新增率为 0"

判断技巧：把指标里的形容词全部删掉，如果句子还能成立就是可验证的；如果删掉形容词就空了，说明在说空话。

### 原则 4：明确边界

优秀 PRD 必须同时说明「做什么」和「不做什么」：

本期做：
- 周报收集 / 周报整理 / 团队汇总

本期不做：
- 自动绩效评分（涉及考核，风险高）
- 自动晋升建议
- 修改员工绩效结果

「不做什么」比「做什么」更难写，也更值钱——它挡住的是未来 80% 的需求膨胀。

### 原则 5：异常流程必须考虑

不仅描述正常情况：
> 用户上传成功 → AI 生成 → 用户导出

还要描述失败路径：
- 上传失败（格式错误 / 超过大小）
- 数据异常（空文件 / 乱码）
- AI 失败（超时 / 返回异常）
- 用户取消（中途退出如何保存）

只写正常流程的 PRD，开发会默认「异常情况不需要处理」，上线必出事故。

## 3. 高级 PM 专项原则（v0.2 / v0.3 沉淀）

以下原则来自真实踩坑，按优先级排列：

### 原则 6：技术实现与产品要求分离
PRD 说「系统需保留原文档字体、图片、分栏」；技术方案说「用 OOXML / 格式转换实现」。两层分开，PRD 不被技术选型绑死。

### 原则 7：按功能复杂度决定写法深度
核心复杂功能写全（目标/流程/规则/异常/验收）；简单功能简写（说明/规则/验收）。不要每个功能硬套九层模板——那不是 PRD，是填表。

### 原则 8：事实边界优先（AI 产品命门）
对 AI 产品，必须定义「哪些内容可以修改、哪些只能读取、哪些绝不能新增」。例如简历改写中：句式/表达可改，公司名/时间/数字禁改。这是 AI 行为边界设计，不是实现细节。

### 原则 9：AI 改写必须可解释
AI 的修改依据必须来自「JD 要求 × 用户已有经历」的交集，而非自由发挥。每条改句应可追溯到「原句 ↔ 改句 ↔ 理由」，理由只能引用来源，不允许生成评价性废话。

### 原则 10：指标必须可定义、可测量
不要写「准确率高」。要定义：什么算错？什么算对？例如「对可验证事实字段，改写后不得新增原简历不存在的实体」——这才是可测的。

### 原则 11：降级方案前置
AI 能力可能达不到预期。PRD 应提前定义：保真等级（A 100% 一致 / B 高度一致 / C 重新排版）、降级路径（人工确认 / 回退 / 提示 / 降低自动化）。不要等开发做不出来再临时问。

### 原则 12：避免重复信息
如果某条规则适用于整个产品（如「仅用户本人可访问」），在文档前面统一写一次，不要每个功能重复。信息密度高 ≠ 字数多。

### 原则 13：PRD 服务协作
写完问自己：设计师看到能画出页面吗？开发看到能写逻辑吗？测试看到能写用例吗？三人中任何一人还需要作者解释，PRD 就不合格。

## 4. 禁止事项（高频雷区）

1. 把需求分析直接复制成 PRD（PRD 是结论的加工，不是搬运）
2. 没有明确价值就堆功能
3. 编造数据、市场规模、调研结论（用「待验证 / TBD / 假设」代替）
4. 把 TBD 偷偷补成事实
5. 大量使用空泛术语（赋能 / 闭环 / 智能化）
6. 只写正常流程不写异常
7. 只写页面不写业务规则
8. 只写 AI 能做什么不写 AI 失败怎么办
9. 写死具体技术实现（某库 / 某框架）
10. 描述内部数据结构而非用户可感知能力
11. 使用模糊质量词（「完全一致」「流畅」）而不给可测标准
12. 把降级决策留给开发
