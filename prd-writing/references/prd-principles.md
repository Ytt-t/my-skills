# PRD 核心原则参考手册

> 本文件是对 `SKILL.md` 中核心原则的提炼，供写 PRD 时快速对照。完整流程与步骤见 `../SKILL.md`。

## 一、PRD 的本质

PRD 的目标是**建立共识**，不是展示文字能力。它要让：

- 产品团队能讨论
- 设计团队能理解
- 开发团队能实现
- 测试团队能验收

写之前先问自己：**这份文档是给人干活用的，还是给人看的？**

## 二、核心原则（4 条）

### 1. 先明确"为什么"，再写"做什么"
不能一上来就是功能列表。先回答：用户遇到了什么问题、为什么值得解决、本次达成什么目标。

### 2. 不把用户想法直接当成最终方案
用户说"我要加一个 AI 总结按钮"——先判断：
- 这个按钮解决什么问题？
- 用户为什么需要它？
- 是否真的需要 AI？
- 有没有更简单的方案？

方案有问题，要指出，而不是机械执行。

### 3. 不编造事实
以下内容不得凭空生成：用户数据、市场规模、调研结论、使用频率、商业结果、技术能力、业务规则。
没有数据时用：**待验证 / TBD / 假设 / 待确认**。

### 4. 不堆"产品黑话"
禁止：提升用户体验、提升效率、赋能用户、打造闭环、增强智能化、提升平台能力、全面优化。
除非写明"具体提升什么、对谁提升、如何判断提升成功"。

## 三、v0.2 七条规则（速查）

| # | 规则 | 一句话 |
|---|------|--------|
| 1 | 技术实现与产品要求分离 | PRD 写"系统应做到什么"，技术方案（库/工具/框架）放技术文档 |
| 2 | 根据功能复杂度决定写法 | 核心功能详写（目标/流程/规则/异常/验收），简单功能简写（说明/规则/验收） |
| 3 | 事实边界优先 | AI 产品必须定义：哪些可改、哪些只读、哪些绝不能新增 |
| 4 | AI 改写必须可解释 | 输入依据、修改依据、结果追溯；依据来自"已有内容 × 需求"交集 |
| 5 | 指标必须可定义、可测量 | 不写"准确率高""幻觉率=0"；要说明什么算对、什么算错、怎么量化 |
| 6 | 避免重复信息 | 适用于整个产品的规则前部统一声明一次，不逐功能重复 |
| 7 | PRD 要服务于协作 | 设计师/开发/测试看完无需作者口头解释 |

## 四、v0.3 五项检查（速查）

1. **产品边界**：这是用户问题还是用户方案？为 AI 而 AI？AI 不能做什么？
2. **技术侵入**：写死技术方案了吗？把实现方式当需求了吗？
3. **AI 产品专项**：输入来源 / 输出格式 / 事实边界 / 幻觉风险 / 可解释性 / 人机协作方式
4. **可落地**：开发知道何时成功、何时失败？测试知道怎么测？
5. **降级方案**：模型做不到怎么办？提前定义等级 + 降级路径，别把决策留给开发。

## 五、写作风格

- 具体、简洁、可执行、少废话、少形容词
- 多写具体行为和条件规则
- 同一信息只表达一次
- 不用复杂术语，不为显得专业而加章节
- 信息密度高 ≠ 字数多

## 六、禁止事项（底线清单）

1. 把需求分析直接复制成 PRD
2. 没有明确价值就堆功能
3. 编造数据和调研结论
4. 把 TBD 偷偷补成事实
5. 大量空泛产品术语
6. 只写正常流程不写异常流程
7. 只写页面不写业务规则
8. 只写 AI 能做什么不写 AI 失败时怎么办
9. 只写"做什么"不写"做到什么算完成"
10. 把"未来可能做"混进本期需求
11. 预设具体技术实现（写死 python-docx / HTML 渲染）
12. 所有功能一律套同一套模板
13. 指标只给模糊形容词而不定义对错标准
14. 功能描述写内部数据结构（"样式/位置映射"）而非用户可感知能力
15. 验收用"完全一致""准确无误"等模糊质量词
16. 不定义 AI 能力降级方案，把决策留给开发

---

**用法**：写 PRD 前扫一眼 §二；写完后用 §三 §四 逐条核对；§六 是红线，踩一条就打回。
