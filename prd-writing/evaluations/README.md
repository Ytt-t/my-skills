# PRD 质量检查清单

> 用途：每次生成 / 评审 PRD 后逐项打勾。覆盖不完整 = 不通过。
> 配套：原则见 `references/prd-principles.md`；AI 专项见 `references/ai-product-prd.md`。

## 评分方式
- 每组全勾 = 通过
- 标 ⭐ 的项为「一票否决项」：不通过则整份 PRD 不合格
- 建议打分：12 组全过 = 合格；AI 产品额外要求「AI 产品专项」组全过

---

## 1. 用户价值 ⭐
- [ ] 是否说明用户痛点（不是功能，是问题）
- [ ] 是否说明为什么现在做
- [ ] 是否避免「为 AI 而 AI」（去掉 AI 仍成立才是真需求）

## 2. 需求完整性 ⭐
- [ ] 是否有用户流程（主路径）
- [ ] 是否有异常流程（失败路径）
- [ ] 是否有范围边界（本期做 / 本期不做）
- [ ] 是否做了替代方案 / 竞品分析（验证需求成立）

## 3. 目标与指标
- [ ] 产品目标是否可验证（无形容词空话）
- [ ] 指标是否可定义（什么算达标）
- [ ] 是否有关键漏斗 / 核心指标

## 4. 功能描述
- [ ] 复杂功能详写、简单功能简写（非机械套模板）
- [ ] 功能描述用用户可感知语言（非内部数据结构）
- [ ] 重复规则是否统一写一次（未逐功能重复）

## 5. AI 产品专项 ⭐（含 AI 功能必查）
- [ ] 是否定义输入
- [ ] 是否定义输出
- [ ] 是否定义能力边界（具体禁做项，非「不编造」三字）
- [ ] 是否考虑幻觉控制
- [ ] 是否有事实边界矩阵
- [ ] 改写依据是否来自「需求 × 已有信息」交集

## 6. 可解释性
- [ ] AI 结果是否可解释（理由有来源）
- [ ] 是否禁止无来源的评价性说明

## 7. 验收标准 ⭐
- [ ] 是否使用 Given/When/Then
- [ ] 是否可测试（无「流畅 / 一致」等模糊词）
- [ ] 核心需求是否覆盖三类场景（正常 / 异常 / 边界）

## 8. 技术侵入检查
- [ ] 是否未写死技术实现（某库 / 某框架）
- [ ] 是否把实现方式当需求

## 9. 降级方案 ⭐（AI / 高风险功能必查）
- [ ] 是否定义保真等级（A/B/C）
- [ ] 是否定义降级路径（人工确认 / 回退 / 提示 / 降自动化）

## 10. 协作可达性
- [ ] 设计师看后能画页面（有页面结构）
- [ ] 开发看后能写逻辑（行为清晰）
- [ ] 测试看后能写用例（验收明确）

## 11. 事实诚信
- [ ] 是否把假设写成事实
- [ ] 无数据处是否用 TBD / 待验证 / 假设

## 12. 产品规划（加分项）
- [ ] 是否有 MVP 版本路线（V1 / V2 / V3）
- [ ] 是否区分核心价值与交付闭环

---

## 迭代闭环
1. 用本清单评估一份 PRD
2. 发现问题记入「待升级项」
3. 累计 3 条同类问题 → 回到 `SKILL.md` 增加对应规则
4. 本 skill 即以此方式从 v0.1 迭代至 v0.3
